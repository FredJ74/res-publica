# PR #219 — correction de l'isolation des fixtures de combat

**Échec CI reproduit et corrigé localement ; certification 1015 toujours bloquée
par l'absence du fichier privé.** Lot corrigé poussé : `7cee2bfe`.

## Journaux et cause démontrée

Exécution signalée `41304385900`, job `124841689748`, SHA `85396976`, étape 43.
L'API GitHub refuse ici la lecture (`Forbidden`). L'intégrateur a transmis les
quatre cas en échec et leurs messages. Les douze premiers essais locaux sans
forçage passaient : ils n'autorisaient aucune conclusion sur la cause.

Le banc parent utilise **deux connexions réellement concurrentes**, qui
committent un round pour vérifier verrou, reçu unique et rejeu. Les dégâts et
morts de ces connexions ne sont pas annulés par le savepoint de la session de
lecture. La suite civile préparait les PJ et les positions, mais laissait ses
PNJ `ancre` et `autre` dans l'état hérité. Selon les vrais coups du round parent,
ils pouvaient donc être morts à l'entrée d'une nouvelle scène.

Reproduction déterministe : appeler le **vrai `pnj_mourir`**, sur le roster
entièrement fictif, avant la suite civile, sans modifier une issue de combat.
On retrouve exactement les quatre cas signalés :

- `civil_cibler_un_accompagnant_engage_le_groupe_reel_et_son_chef` : affecter un
  leader au PNJ mort viole correctement `pnj_mort_sans_leader`.
- `civil_PNJ_gamma_protege_meme_par_appel_direct` : le PNJ mort est exclu des cibles
  avant l'examen du profil gamma, d'où `cible_non_referencee`.
- `armee_recrutement_et_round_mixte_preserves_apres_extraction_commune` : dans la
  reproduction, seuls les quatre PJ sont recrutés et l'assertion `effectif > 4`
  échoue. Le message CI original était vide : cette ligne est démontrée pour la
  reproduction, pas prétendue extraite du journal distant.
- `civil_nom_PNJ_unique_resolu_vers_identite_canonique` : même exclusion correcte
  d'un mort avant résolution de son nom.

Les trois erreurs directement liées à `ancre` sont aussi reproduites sur 17.6.
La contre-épreuve finale reproduit les **quatre** sur 17.6. Passer simplement la
CI de 16.2 à 17.6 n'aurait donc pas résolu ce défaut d'isolation.

## Correction ciblée et garde métier conservée

Au début de **chaque nouvelle scène fictive**, ses deux PNJ propres retrouvent
les préconditions explicites « actif / PA maximum ». Ce reset est dans le banc,
connecté exclusivement à PostgreSQL jetable. Aucune fonction SQL du jeu,
contrainte, permission, règle de combat, métier ou propriétaire n'est modifié.
Il ne s'applique pas au milieu d'un combat ni à un PNJ réel.

Tous les **379 cas précédents** sont conservés. Un **380e** vérifie, après une
nouvelle vraie mort dans le scénario : cible refusée, aucun PA dépensé, leader
interdit par la même contrainte et PNJ toujours mort après le refus. Il interdit
de « corriger » cette régression en affaiblissant la règle serveur.

La CI lance la suite avec `--fixture-roster-mort` : même si le tirage du round
parent est favorable, cette précondition défavorable reste exercée à chaque
passage, sans réduire la suite. `--contre-reset-fixture` retire volontairement
le reset dans la base jetable et réintroduit les quatre échecs ; code de sortie 1.

Les assertions vides conservent désormais type, fichier, ligne et trace. Le JSON
fictif est écrit atomiquement hors dépôt, dans l'artefact **déjà existant**
`bancs-client`, via `HG219_RAPPORT_JSON`. Aucun `continue-on-error`, aucune
assertion retirée, aucun `|| true`, aucun pipeline supplémentaire.
